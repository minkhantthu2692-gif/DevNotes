PROJECT: DevNotes — Personal Programming Knowledge Workspace

1. ROLE AND OBJECTIVE

Act as a senior frontend engineer, UI/UX designer, database architect, and application security engineer.

Build a complete, production-minded web application called DevNotes: a personal programming knowledge library for learners who want to organize, preserve, review, and apply their programming knowledge.

This is not merely a dashboard mockup or a CRUD demonstration. Build a genuinely usable application with working features, persistent data, offline support, cloud synchronization, authentication, a customizable editor, and an AI learning assistant.

The owner is learning programming through self-study and wants to maintain this project independently. Code readability, understandable comments, straightforward setup, maintainability, and minimal operational complexity are critical requirements.

Make sensible engineering decisions independently when they improve usability, reliability, security, or maintainability. Do not blindly follow requirements if a technically superior solution achieves the same goal with fewer complications.

2. NON-NEGOTIABLE TECHNOLOGY REQUIREMENTS

Core frontend

- HTML5
- CSS3
- Vanilla JavaScript using native ES modules where supported
- No React, Vue, Angular, Svelte, or other frontend framework.
- No TypeScript compilation requirement.
- No Python runtime.
- No Node.js application server.
- No mandatory local development server.
- No mandatory bundler or build step for the normal application.
- No server-side application that must be running continuously on the user's PC.

Use JavaScript libraries when they provide meaningful functionality that would otherwise be unnecessarily difficult to implement safely.

The application must be deployable as a static website. Prefer native browser APIs and modular JavaScript.

Use a pinned, compatible version of each third-party library. Do not load dependencies dynamically from untrusted sources at runtime.

The main application should work from static hosting over HTTPS. Support opening the application locally where browser capabilities permit, but do not falsely promise that every cloud, authentication, module, or service-worker feature will work from file://.

Backend services

Use Supabase for:

- Authentication
- PostgreSQL database
- File storage
- Realtime updates when useful

Use Groq API for AI features.

Use IndexedDB for local application data and offline-first operations.

Do not use Firebase.

Do not introduce another cloud database, object storage provider, or mandatory backend service unless a documented technical limitation makes it necessary.

Optional server-side component

If a server-side function is necessary to protect shared AI credentials, use a Supabase Edge Function as an optional, deployable JavaScript/TypeScript component.

This function must not require a permanently running local server. Deployment and configuration instructions must be documented.

The static application must still support a personal BYOK AI mode where the user supplies their own Groq API key.

Never expose a privileged API key or service-role key in frontend code.

3. PROJECT PRINCIPLES

Prioritize these principles in order:

1. Data integrity and recoverability.
2. Security and privacy.
3. Reliable offline operation and synchronization.
4. Excellent everyday usability.
5. Clear, maintainable architecture.
6. Responsive and accessible design.
7. Minimal setup and deployment complexity.
8. Performance and visual polish.

Do not sacrifice correctness for visual effects or excessive abstractions.

Do not create decorative buttons, simulated functionality, fake progress, or placeholder actions that appear implemented.

Every visible control must work, or be explicitly marked as unavailable until configured.

Never silently discard user data.

Units and spacing

Typography and fonts

Respect font licensing. Do not bundle unlicensed fonts.

Design for desktop first, then adapt to tablet and mobile.

- Make editor panes stack or switch modes.

- Keep essential actions reachable.
- Adapt dialogs and command palette dimensions.

Custom components

17. LOCAL-FIRST DATABASE AND OFFLINE SUPPORT

IndexedDB is the primary local persistence layer.

Implement a modular data access layer rather than accessing IndexedDB directly from UI components.

Possible modules:

- database.js
- repositories/
- migrations/
- sync-engine.js
- sync-queue.js
- conflict-resolver.js
- connectivity.js

Use a maintained IndexedDB wrapper such as the idb library if it reduces complexity and is compatible with the static architecture.

Offline requirements

When offline, users must be able to:

- Open previously cached lessons
- Create lessons
- Edit lessons
- Delete or restore lessons
- Manage categories and tags
- Search locally stored content
- Use code snippets
- Change local preferences
- Review saved study materials
- Export local data

AI requests and other network-dependent operations must display a clear unavailable state when offline.

Sync engine

Build an explicit synchronization engine for local-first operations.

Requirements:

- Persistent operation queue.
- Idempotent operation handling.
- Automatic retries with exponential backoff and jitter.
- Retryable versus permanent error classification.
- Stable record IDs generated locally.
- Pending, syncing, synced, and failed statuses.
- Safe handling of offline deletes.
- Queue recovery after reload or browser restart.
- Network recovery detection.
- Manual retry.
- Duplicate prevention.
- Conflict detection.
- User-visible synchronization status.

Do not assume that navigator.onLine proves the backend is reachable. Verify actual connectivity with appropriate requests.

Use a single-flight or equivalent lock to prevent overlapping synchronization runs from processing the same queue incorrectly.

Conflict handling

Never silently overwrite conflicting content.

Use revision numbers or another explicit versioning strategy, along with timestamps and ownership checks.

If a remote record has changed since the local base version:

- Detect the conflict.
- Preserve both versions.
- Offer a comparison view.
- Allow the user to choose the local version, remote version, or merge content where practical.
- Record the resolution.

Timestamps alone are not a sufficient conflict-resolution strategy.

Do not permanently delete data until the relevant deletion has synchronized safely.

Service worker

Use a service worker for offline application-shell caching when deployed over HTTPS or localhost.

Cache versioned static assets and approved dependencies.

Do not cache authenticated API responses indiscriminately.

Do not assume a service worker can operate from file://.

Document how to update cached application assets without losing user data.

26. IMPLEMENTATION STRATEGY

Phase 2: IndexedDB, data models, local CRUD, search, editor, code blocks.

Phase 3: Settings, themes, fonts, import/export, review tools.

Phase 4: Supabase schema, RLS, authentication, cloud repositories.

Phase 5: Sync queue, conflict detection, offline recovery, service worker.

Phase 6: Groq AI assistant and optional server-side proxy.

Phase 7: Testing, accessibility, responsive polish, documentation.

At each phase:

- Implement actual functionality.
- Verify the relevant behavior.
- Keep existing working functionality intact.
- Fix errors before adding more features.
- Update documentation when architecture changes.

Do not stop after generating a static mockup or initial file structure.

Do not claim completion while core actions are placeholders.

If credentials are unavailable, implement the integration correctly and provide a clear setup flow. Test the parts that do not require credentials and document what remains unverified.

27. DEFINITION OF DONE

The project is complete only when:

- The UI is polished, responsive, and accessible.
- Core note operations work without a network connection.
- Data persists after browser reloads.
- Search and sorting work on real saved records.
- Code blocks are highlighted and copyable.
- User preferences persist.
- Import/export works with validated data.
- Cloud authentication works after configuration.
- Database ownership is enforced by RLS.
- Cloud synchronization is idempotent and conflict-aware.
- Network errors do not destroy local changes.
- AI is optional and its configuration is understandable.
- No shared API secrets are exposed in the frontend.
- Loading, success, empty, and error states are implemented.
- The README provides usable setup and deployment instructions.
- The project contains understandable comments explaining non-obvious logic.
- No core feature is represented by a decorative or nonfunctional control.

Start by inspecting the current project if one exists. Then create or update the architecture and implement the application incrementally. Make reasonable decisions without repeatedly asking the user to approve routine technical details.
